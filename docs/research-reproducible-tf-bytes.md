# Research: byte-reproducible Text-Fabric output (#122)

## Scope

TLHdig-TF's current-build manifest hashes the generated `.tf` files byte-for-byte. During #118, a hosted clean rebuild of unchanged corpus semantics passed every validation gate but produced a different output-tree digest from the already committed `0.4.0` artifact. This research identifies the source of that drift and defines the narrow boundary for a later fix.

This ticket is about deterministic generated bytes for identical source/code/dependency inputs. It does not reintroduce historical release certification, change the corpus schema, remove historical version directories, or solve dependency locking.

## Observed failure mode

PR #119 changed build orchestration: it resets the current generated directories before conversion and makes required preflight inputs fail closed. It did not change converter/schema semantics.

A clean hosted build on production-code commit `c2544490f9b8efdd7dc1e5a2af4d27cbe12646fc` completed successfully and passed the complete 16-gate `validate_current.py` sequence, yet the generated output hashes differed from the committed current artifact across essentially the full `.tf` set. Therefore a successful clean rebuild cannot currently be assumed to reproduce the same bytes.

The direct build-manifest contract makes this visible rather than hiding it: a manifest emitted by that clean build describes the hosted build's bytes, not necessarily the bytes already committed in Git.

## Upstream Text-Fabric writer

Text-Fabric 13.1.0 was inspected in `annotation/text-fabric`, `tf/core/data.py` at commit `0c45c386916cb52be84098796ec27ce97e5bf9fc`.

For every feature file, the writer emits the feature/config/edge marker, then caller metadata in sorted-key order, then unconditionally writes:

```text
@writtenBy=Text-Fabric
@dateWritten=<current UTC wall-clock time>
```

`dateWritten` is constructed from `utcnow()` at save time. It is not taken from caller metadata and there is no caller-facing parameter in this write path to supply a deterministic value.

This alone guarantees that two saves of the same logical feature at different seconds have different bytes.

The same inspected writer is otherwise deliberately ordered at the serialization boundary relevant here:

- metadata keys are sorted before writing;
- node and edge source node ids are sorted;
- ranged node output is sorted by node-range endpoints;
- valued edge groups are sorted before serialization;
- WARP tuple data is reconstructed into node-keyed data and then follows the same ordered writer.

That does not prove the entire TLHdig conversion is deterministic, but it makes `dateWritten` the only explicit wall-clock input found in the Text-Fabric text writer itself.

## TLHdig-TF's existing deterministic boundaries

The converter already removes several common sources of ordering drift:

- `programs/tlhdig/paths.py::corpus_files()` sorts source XML paths by NFC-normalized lowercase path, preventing filesystem/macOS normalization from changing document/node order;
- the generated current artifact is closed-world hashed by `build_manifest.py`;
- `programs/tlhdig/compact.py` is already a post-save rewrite stage. It walks `*.tf` files in sorted filename order, parses node-feature data, groups equal values, sorts node ids, and writes deterministic compacted node-feature bodies.

The compactor currently preserves the Text-Fabric header verbatim, including `@dateWritten`, and only rewrites node features. Non-node/config/edge/WARP files retain the upstream header untouched.

## Candidate designs

### A. Normalize generated `dateWritten` after save — preferred

At the build-output boundary, rewrite every generated `.tf` file header and remove or replace only the volatile Text-Fabric-generated `@dateWritten` line. Apply it to all `.tf` file kinds, not only node features.

Two variants are viable:

1. remove `@dateWritten` entirely;
2. replace it with a deterministic value derived from build identity.

Removal is the smaller semantic claim. The timestamp is writer bookkeeping, not corpus data, and Text-Fabric's own dataset-modification code classifies `dateWritten` with generated metadata. A deterministic pseudo-timestamp would look like a real wall-clock fact while no longer meaning that, so it is less attractive unless a consumer demonstrably requires the field.

Keep `@writtenBy=Text-Fabric`: it is deterministic and truthfully describes the serialization format.

The normalization should be an explicit TLHdig-TF post-save operation, not a monkey-patch of installed Text-Fabric code.

### B. Canonicalize only when hashing — rejected as the primary fix

The manifest could ignore `@dateWritten` while leaving the files volatile. This would make the manifest's logical digest reproducible, but the repository artifact itself would still change on every build. Git diffs, caches, downloads, and reproducibility claims would remain noisy. It also weakens the current manifest's useful byte-integrity semantics.

### C. Patch/fork Text-Fabric writer — rejected for this stage

Changing site-packages or carrying a fork solely to inject a timestamp policy creates dependency and maintenance surface disproportionate to this problem. TLHdig-TF already owns a post-save normalization/compaction boundary.

## Natural implementation boundary

`programs/tlhdig/compact.py` is a suitable location conceptually because it already owns deterministic post-save rewriting, but timestamp normalization must not be hidden inside `compact_file()` because that function intentionally returns `False` for non-node features.

A narrow helper such as `normalize_generated_metadata(path)` / `normalize_dir(d)` can operate on every regular `*.tf` file, after Text-Fabric has saved the complete module and before output hashing/validation. Node-feature compaction can remain a separate operation.

The build owns both current module trees. Provenance features are moved from main output only after compaction today, so sequencing needs care: normalization must cover all final generated `.tf` files exactly once, including provenance files after their move, or normalize before the move in a way that covers them while still in the main directory.

The cleanest candidate sequence to test is:

1. Text-Fabric conversion writes main output;
2. normalize volatile generated metadata for all `.tf` files in main output;
3. compact node features;
4. split/move provenance features and generate provenance README;
5. optionally assert/normalize final provenance `.tf` tree as a defensive final boundary;
6. validate and hash final output.

No generated timestamp should be added to the provenance README or manifest as a substitute.

## Compatibility questions

`dateWritten` is metadata, so removing it should not affect node/edge/config data loading. Nevertheless the TDD implementation must prove rather than assume compatibility:

- Text-Fabric loads a normalized synthetic feature without error;
- app/config validation sees no change in corpus features/formats;
- current census/structure/morphology/sign/provenance gates remain unchanged;
- Context-Fabric/Agora consumption, which requires the TF data path and `otype.tf`, does not rely on `dateWritten`;
- no project code reads `dateWritten` as a required field.

Repository search currently gives no TLHdig-TF runtime dependency on `dateWritten`; upstream Text-Fabric itself treats `writtenBy`, `dateWritten`, and `version` as generated metadata in dataset-modification code.

## What is not yet proven

Removing `dateWritten` is necessary for byte reproducibility, but research must not overclaim that it is sufficient. The full converter and environment may contain another source of nondeterminism not visible in the inspected Text-Fabric writer.

The decisive integration experiment is therefore two independent clean builds of the same exact commit, source tree, and dependency specification after normalization. Their closed-world output manifests must have identical output file sets and hashes. If they differ, compare per-file diffs before broadening the normalization contract.

This experiment belongs in the implementation gate because the current code cannot produce normalized builds yet.

## TDD implications

The RED phase should establish the smallest observable contract before production changes:

1. create representative synthetic `.tf` files with identical metadata/data but different `@dateWritten` values and prove current output bytes/digests differ;
2. include node, edge/config or WARP-shaped files so the fix cannot accidentally normalize only files that the compactor rewrites;
3. require normalization to preserve every non-`dateWritten` byte/line and be idempotent;
4. require normalized files to load through Text-Fabric where practical;
5. require directory normalization to reject or fail closed on unexpected symlinks rather than following them outside the generated tree;
6. then implement the minimal post-save normalization.

After unit GREEN, run a complete hosted clean build and all 16 current validation gates, then run a second independent clean build on the same exact production-code commit. The two final output digests must match before this ticket is considered solved.

## Relationship to #118 and #115

#118 and #122 solve different invariants:

- #118 ensures a new build cannot inherit obsolete files from an older build;
- #122 ensures two clean builds of the same inputs do not differ merely because they ran at different times.

#115's removal of historical `0.1.0`–`0.3.0` trees does not need to wait for #122 as long as the committed current `0.4.0` artifact has a manifest that validates its actual bytes. #122 improves rebuild reproducibility; it does not make historical siblings necessary.

## Conclusion

The clean-build byte drift is real and at least one root cause is confirmed upstream: Text-Fabric injects wall-clock `@dateWritten` into every saved feature. The preferred fix is a narrow TLHdig-TF post-save normalization that removes this generated volatile header from all generated `.tf` files while preserving byte-level manifest semantics. A two-clean-build exact-digest experiment is required to prove that no second nondeterministic input remains before the issue can close.
