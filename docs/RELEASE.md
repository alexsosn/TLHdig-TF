# Building and validating the current TLHdig-TF artifact

TLHdig-TF is currently pre-alpha. `main` carries one supported current generated corpus; generated pre-1.0 snapshots are not a compatibility contract. Git history and intentionally cut GitHub tags/releases preserve development history when needed.

The current artifact is `tf/<TF_VERSION>` with the optional provenance module at `tf-provenance/<TF_VERSION>`. At present `TF_VERSION` is `0.4.0`. During pre-alpha, the contents of that directory may be replaced when the converter or schema changes.

## Normal build sequence

From a clean checkout with the pinned TLHdig source present:

```bash
python programs/build.py
python programs/validate_current.py
python programs/check_build_manifest.py
```

To stage the validated generated corpus deliberately:

```bash
bash programs/publish_dataset.sh
```

`publish_dataset.sh` refuses to stage generated bytes unless the current build manifest still matches them.

## Current validation

`programs/validate_current.py` runs the substantive source/corpus/app checks against one unchanged artifact:

- source corpus identity and repair-manifest validity;
- sign/source round trip;
- morphology and structural conservation;
- sign-language conservation;
- manuscript joins and Contract-A graph/source checks;
- marker and XML-tag conservation;
- provenance-module split checks;
- cuneiform alignment and locked external sign-reference checks;
- Text-Fabric app/config validation;
- a fresh-process Text-Fabric load and census.

External sign-reference checks run in their strict `release` mode during complete current-build validation: an unavailable or explicitly skipped reference source is not converted into a successful validation.

The validator also snapshots the reproducibility inputs, executable/config identity, generated main/provenance output identity, and Git HEAD before the gate sequence. It recomputes them afterward. Input, code, output, dirty-tree, or HEAD drift makes validation fail.

## `BUILD-MANIFEST.json`

A successful run writes:

```text
tf/<TF_VERSION>/BUILD-MANIFEST.json
```

The manifest directly records:

- source and current TF schema/converter versions;
- the producing Git commit as provenance;
- SHA-256 identities of the source manifest, repair manifest, exclusion ledger, external sign-reference lock, and dependency specification;
- SHA-256 identity of the executable/config files used by current conversion and validation;
- a closed-world per-file inventory and aggregate hash of the current main and provenance modules;
- the fixed ordered set of substantive validation gates and `success: true`.

Output identity includes module membership, so moving a feature between `tf/` and `tf-provenance/` changes the artifact identity. Missing, changed, or extra regular files also change it. Text-Fabric's derived `.tf/` binary caches and the manifest itself are excluded. Symlinks fail closed rather than being followed outside the artifact tree.

`programs/check_build_manifest.py` independently recomputes these identities. It does not require the manifest's producing commit to equal the repository's later `HEAD`: committing the manifest itself necessarily creates a later commit. Current input, executable/config, and generated-output hashes are the active drift contract.

## Reproducibility boundary

The current inputs include `programs/corpus.sha256`, `programs/patches.yaml`, `programs/excluded.txt`, `programs/signrefs.lock.json`, and `requirements.txt`. `requirements.txt` pins direct Python dependencies; full transitive environment locking is tracked separately in issue #106.

The generated corpus must be reproducible from pinned source identity + converter + declared dependency environment. Issue #118 tracks an additional clean-output invariant: rebuilding must not leave obsolete feature files from a previous schema behind.

## CI

`.github/workflows/ci.yml` runs the fast/unit/integration checks against the committed current artifact and verifies its build manifest. `.github/workflows/dataset.yml` is the hosted clean rebuild path and runs the complete current validator after conversion.

There is no write-enabled certification workflow during pre-alpha. Validation does not commit evidence back into the branch.

## Historical release-certification documents

Older research/plan documents may describe `BUILD-COMPLETE`, `RELEASE-CERTIFICATION.json`, `release-v3`/`release-v4`/`release-v5`, or predecessor-delta certification. Those files document earlier development decisions; they are not the active pre-alpha build contract.

The historical certification stack was retired when the project adopted the one-current-artifact policy in issues #115/#116. If TLHdig-TF later enters a compatibility-bearing stable release phase, publication/version-retention guarantees can be designed around actual users and citation requirements rather than inherited from the pre-alpha machinery.
