# Research: clean current-artifact rebuild output (#118)

## Scope

Issue #118 closes a correctness gap left intentionally after #116: `programs/build.py` rebuilds the mutable current Text-Fabric artifact in place, so a feature that the current converter no longer emits can survive from an older build and then be hashed honestly into a new `BUILD-MANIFEST.json`.

This research is limited to current generated-output ownership and cleanup semantics. It does not remove historical sibling versions, redesign publication, or change corpus/schema semantics.

## Current repository behavior

The current build owns two version directories:

- `tf/<TF_VERSION>/`: generated TF/config features, generated `LICENSE`, and after validation `BUILD-MANIFEST.json`;
- `tf-provenance/<TF_VERSION>/`: generated provenance features plus generated `README.md`.

`programs/build.py` currently calls `clear_validation_metadata(out)` before conversion. That removes only `BUILD-MANIFEST.json` and the retired certificate files from the main module. It does not delete unrelated `.tf` features, provenance leftovers, or derived `.tf/` caches.

`split_provenance()` creates/reuses the current provenance directory and replaces only the provenance features emitted by this run. Therefore stale provenance output can survive for the same reason as stale main output.

## Upstream Text-Fabric writer behavior

Text-Fabric 13.1.0 was inspected at `tf/core/fabric.py::FabricCore.save`. The writer iterates only the feature objects supplied for the current save and calls each feature object's `save(..., overwrite=True)`. That overwrites emitted features but does not enumerate and remove unrelated `.tf` files already present in the module directory.

That source behavior is enough to establish the failure mode: an obsolete feature is outside the current save set, so ordinary overwrite semantics never touch it. Text-Fabric code that needs replacement semantics uses explicit destination-directory removal elsewhere (for example volume collection), rather than relying on `save(overwrite=True)` to prune a directory.

The RED phase will reproduce the repository consequence directly with filesystem/build orchestration fixtures; no live corpus crawl is needed.

## Ownership boundary

For the one current pre-alpha version, the build owns the complete two version-directory trees. Nothing inside either directory is hand-maintained state that must survive a rebuild:

- main TF/config features are generated;
- provenance TF features are generated;
- main `LICENSE` is generated by `write_dataset_license()`;
- provenance `README.md` is generated by `split_provenance()`;
- `BUILD-MANIFEST.json` is generated only after complete validation;
- retired certificate files are obsolete generated metadata;
- `.tf/` caches are derived and disposable.

Sibling version directories such as `tf/0.3.0` and `tf-provenance/0.3.0`, repository source/configuration, and anything outside the exact current version directories are not owned by this cleanup.

## Failure model

A feature-level prune list would duplicate converter schema knowledge and can itself become stale. The safer contract is directory-level replacement of exactly the current owned trees before generation.

A failed rebuild may leave an incomplete new current tree. That is acceptable in the present pre-alpha workflow because availability of the previous generated tree is not a requirement. It is safer than preserving a half-old/half-new graph. #116 now supplies the fail-closed validation invariant: cleanup removes the old manifest, and a partial failed build cannot pass `check_build_manifest.py` until a complete build is validated again.

Atomic two-directory replacement is therefore unnecessary complexity here and would temporarily require a second full artifact on disk.

## Safety requirements

Cleanup must fail closed before deletion when a target is suspicious:

- reject the current main or provenance path if it is a symlink;
- require each target to be exactly one direct child of its expected `tf/` or `tf-provenance/` parent;
- do not accept nested paths, parent traversal, the parent directory itself, or arbitrary repository paths;
- do not glob across versions;
- never follow a symlink to delete an external target.

Source identity and exclusion configuration should be read/validated before destructive cleanup. Cleanup then occurs immediately before converter output, so an invalid source snapshot does not destroy a usable current artifact while a converter failure cannot inherit old generated bytes.

## Chosen design

Add a small reset primitive in `programs/build.py` (or a narrowly scoped helper module if testability requires it) that receives current main/provenance paths plus their expected parents. It validates both targets first, then removes both owned trees if present, and recreates the main output directory. `split_provenance()` continues to create the provenance directory when needed.

`clear_validation_metadata()` becomes redundant and should be removed from the normal build path; whole-tree cleanup subsumes it.

## TDD implications

RED must demonstrate at least:

1. stale `obsolete.tf` in current main is removed;
2. stale `obsolete.tf` in current provenance is removed;
3. old manifest/certificate files and `.tf/` caches cannot survive reset;
4. sibling version directories survive unchanged;
5. symlinked current output fails closed and its target is untouched;
6. nested/incorrect target paths fail closed without deleting anything;
7. a simulated converter failure happens only after the old manifest/tree has been removed;
8. a small synthetic successful build cannot retain a stale feature from the previous output state.

Tests should use temporary directories and stubbed/synthetic conversion; the full 24k-document corpus is reserved for the hosted integration gate after unit GREEN.

## Review focus

The independent review should attack the cleanup from both sides: try to make it delete outside the current version directories, and try to make old generated state survive. Particular attention belongs to symlinks, path containment/direct-child checks, sibling versions, provenance recreation, converter failure, and compatibility with the #116 manifest/staging flow.

## Conclusion

The defect is real and is a build invariant problem, not a manifest-verification problem. The minimal robust fix is to reset exactly the two converter-owned current-version directory trees immediately before conversion, after immutable-input preflight, with strict path/symlink checks. This makes rebuild output a function of pinned inputs plus current converter output rather than of whatever files happened to be left by the previous schema.
